# MVP 之后的第二期开发路线

日期：2026-10-07（Asia/Hong_Kong）。MVP 基线：main `ce66affa3a0bf6ee76efde60dccb83c1ce396e46`。当前已 claim 的开发票是 [#51](https://github.com/12bitsD/agent4novel/issues/51)；本路线用于界定第二期，不表示下列所有票已开始或已承诺在同一版本交付。

## 1. 第二期目标

第二期把 MVP 从“可以逐章写作”推进到“可以观察、修改、版本选择和安全再生”。回退语义留给相关票据在方案阶段确认。核心反馈链是：

> 发现问题 → 看实际输入输出 → 修改一个因素 → 必要时比较 A/B → 保留评论 → 再继续。

第二期应优先解决三个事实：

1. Agent 和作者能看清节点实际拿到什么、产出了什么。
2. 重新生成和版本选择不会覆盖错误结果，也不会把旧结果误当成新基线。
3. 作者修改设定、章纲或章节规划时，系统明确显示影响范围，避免悄悄改写后续内容。

## 2. 第二期核心范围

### 2A — 工程反馈基础

**#51 节点实际输入输出记录与 Agent A/B + comment** 是当前第一票，必须先做。

交付内容：

- `run-step` 可选保存一次本地实验记录。
- 记录实际传给 SDK 的 system/user 内容、可确认的模型参数、代码版本、最终节点结果或失败状态。
- Agent 可以直接读取结果、复用可比的历史 A、运行新的 B、保存用户原话 comment。
- 不新增评阅平台、评分系统、自动 judge、采用卡或作品数据写入。

**#46 SQLite 首次并发建库修复** 紧随其后，属于第二期基础可靠性要求。

交付内容：

- 两个进程同时首次打开空数据库时，初始化和 seed 结果正确且不重复。
- 只对可重试的 SQLite 锁竞争做有界处理。
- 迁移失败、损坏数据库、未知 schema 和其他错误继续失败并保留安全诊断。
- 已有库重开、CAS 写入、进程终止恢复保持原语义。

第二期不把 #51 的本地实验记录改成 SQLite 实验平台。两者的存储目的不同：#51 是 Agent 本地迭代材料，#46 是作品数据库可靠性。

### 2B — 作者内容迭代

**#12 重新生成入口**建议只取其中的低风险核心；这不是对现有复合 issue 验收标准的静默改写，开工前需回写 issue 或拆出实施票：

- 创意稿失败后的明确重试。
- 作者补充一句想法后重新生成。
- 失败不留下半份方向包，成功才替换当前待审内容。

#12 中的渐进展示、SSE、超长素材分段提炼和版本回看 UI 拆成后续票，不自动并入第二期。

**#20 章纲新旧版本比较与选择** 随后开发。

建议首期范围（具体回退语义由 #20 开工时确认）：

- 重新生成章纲产生可比较的新版本。
- 作者能看到旧版和新版，选择保留哪一版；是否提供“回退”动作由该票方案和验收标准确认。
- 选择动作绑定明确的产物 ID/版本。
- 未选择的新版本保留为历史结果，不能覆盖当前正式基线。

**#21 章节重生**建议排在 #20 之后；这只是路线顺序，不是 GitHub 原生依赖。

交付内容：

- 先确定正文生成后重新规划的对象范围，再实现；当前不承诺本章或后续章纲均可重生。
- 旧正文、后续章节和当前通过状态的保留规则先写清，再实现。
- 新章纲与正文重新生成必须检查版本和来源，旧结果不能被静默覆盖。
- 与 #6 的跨章衔接提示复用，不自动把所有后续章节退回或重写。

#20 是 #21 的建议前置阅读和版本语义基础。没有可选择的章纲版本，章节重生容易变成不可解释的覆盖操作。

### 2C — 设定演进的设计入口

**#18 冲突检测与作者澄清** 进入第二期的设计阶段，不直接承诺完整实现。

设计阶段需要回答：

- 普通缺失信息、真实冲突和作者有意保留的模糊性如何区分。
- 提示是否阻断通过，误报如何处理。
- 作者确认后的结果如何被下游节点消费。

**#17 通过后编辑与扩展设定** 作为 #18 之后的候选实现，不列入第二期核心退出条件。

原因是通过后设定修改会影响已有正文、大纲、待生成章节和未来的作品 Wiki；在没有明确版本、影响提示和回退规则前，直接开放编辑容易产生事实漂移。第二期可以先完成“新增设定的安全设计”或小范围原型，完整设定演进放入下一期。

## 3. 不纳入第二期核心

### 第三期：作品知识与工具能力

**#28 设定查询工具与有界工具执行循环**和**#29 作品 Wiki 与档案演进**共同构成第三期方向。

两票需要共同定义：

- 设定条目的稳定 ID、版本和来源章节。
- 搜索结果与读取结果的作用域和预算。
- 正文/章纲与档案候选的联合审阅和原子生效。
- 工具失败、空结果、超时和重复提交的语义。

#28 可以先做只读正式设定查询，但不能在 #29 的版本与联合通过语义没有确定前，声称完成作品 Wiki。#29 仍是更大的长期能力，不在第二期核心交付中展开。

### 技术整理项

**#15 Hono RPC 类型收敛** 是接口稳定后的工程整理，不解锁作者能力，也不作为第二期排期门槛。只有当新增端点导致类型漂移实际增加维护成本时再安排。

### 长篇质量与模型质量

不把真实模型文学质量、50万字稳定产出、跨作品收益和长时间成本评估写成第二期交付条件。它们需要独立实验和明确预算，不能由工程测试代替。

## 4. 推荐顺序

| 顺序 | 票/工作包 | 类型 | 退出条件 |
| --- | --- | --- | --- |
| 1 | #51 | 当前开发 | Agent能记录并读取一次节点实际输入输出，完成一轮修改、复跑、A/B（按需）和 comment |
| 2 | #46 | 可靠性修复 | 可控 SQLite 并发首次建库测试通过，已有库/迁移/CAS/终止恢复回归通过 |
| 3 | #12 核心子范围 | 作者入口 | 创意失败可重试，补充想法可重新生成，失败不落半份内容 |
| 4 | #20 | 版本选择 | 章纲新旧版本可读、可选；回退语义按票面确认，旧版本不冒充当前基线 |
| 5 | #21 | 章节回流 | 章节重生版本和来源明确，旧章/后章状态有确定保留规则 |
| 6 | #18 设计 | 设计票 | 冲突分类、提示、作者动作和下游消费契约确定 |
| 7 | #17 小范围原型或实现 | 候选 | 只有在 #18 的版本/影响/回退语义通过后才进入实现排期 |

#28/#29、#15 和 #12 的其他子范围不在这条核心顺序内。

## 5. 第二期整体退出条件

第二期完成需要同时满足：

- Agent可以在不修改作品数据的实验目录中复现一次节点迭代，并读取输入、输出、版本和 comment。
- SQLite首次并发初始化不再出现已知的偶发失败，且没有吞掉不可重试错误。
- 创意稿和章纲支持安全再生与版本选择，章节重生不会静默覆盖旧内容。
- 设定冲突至少完成明确的设计契约；未完成的通过后设定编辑不伪装成已支持。
- 生产流程、作者通过语义、CLI未知结果恢复和现有作品数据保持兼容。
- 每张实际开发票分别通过项目的 TDD、Wiki、双轴 review、CI 与远端回读流程；不以“第二期计划写完”替代票据完成。
