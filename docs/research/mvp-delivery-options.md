# #19 内部 grilling：三案研究与选型

基线：只读核对当前代码与 GitHub #19 AC；未修改仓库、未运行测试。已完整读 checklist/Wiki skill。以下是方案结论，不代表实施完成。

## 研究一：按信任边界收敛（推荐主体）
共享 `kind → content schema`；保留 Store 接缝，在写入、状态转换、恢复读取、HTTP 输出和客户端入口复用验证。公开请求/响应移到 contracts，Step 包装仍私有。
适合当前单服务和即将落地的 SQLite；改动可按边界切片，迁移成本最低。代价是通用 Artifact 的类型不能自动随 kind 缩窄，必须明确验证入口，防止遗漏。
证据：`packages/contracts/src/artifacts.ts:33–49` 内容仍是任意 JSON；`apps/server/src/store/in-memory-store.ts:99–130,133–169` 写入尚无内容校验；`packages/contracts/src/public-api.ts:11–35` 仅三类产物额外校验。

## 研究二：完整判别联合贯穿领域

六种 Artifact 形成由 schema 派生的联合，Store 泛型将 kind 与内容绑定，Pipeline/客户端按 kind 得到静态类型；运行时仍校验外部和持久化数据。
适合产物持续扩张、跨包误用频繁时；编译期能发现更多错配。代价是动到动态 Pipeline、夹具和 Store 泛型，容易把治理票扩大成整体类型重构。
证据：`packages/contracts/src/artifacts.ts:4–5,51` 类型入口；`apps/server/src/store/in-memory-store.ts:99–103` 当前 kind/content 分离；私有 Step 已复用共享形态，见 `apps/server/src/steps/setting-io.ts:1–12`。

## 研究三：端点契约登记表驱动

每个 HTTP 端点登记请求、成功、错误 schema，客户端薄封装和路由验证共用登记；底层配相同内容映射/Store 校验，不引入 RPC。
适合端点快速增长、Web/CLI 漂移成为主要成本时；协议覆盖可枚举。代价是登记表与路由衔接的新抽象，目前端点少，生成器/通用适配器收益未证实。
证据：`apps/server/src/routes/works.ts:34–90` 内联请求；`apps/web/src/api.ts:16–50` 配置/列表等缺运行时解析；`:79–93` 部分端点已有共享解析。

## 综合决定与验收

采用一，吸收二的 schema 派生内容映射类型；三先落实“拥有者→生产者→消费者→验证点”清单，不建生成框架。保持所有产品流程、版本/CAS、unknown 回读语义；pending 正文允许编辑态，approved 才用正式内容约束（`public-api.ts:26–28`）。

验收：六 kind 错配及非法存储零写入；状态升级复验；读取损坏数据安全失败；所有公开 DTO 共用；协议异常不误判写入未发生、不自动重放；Step 注入 ID 后复验；现有多章/编辑/并发测试通过。向 #9 交付可复用校验及适配器测试约束。

关键待 Human 决策：无。旧数据迁移、部署目标属于后票。待验证：现有夹具兼容性、循环 import、全部端点覆盖、响应失败后的恢复语义；实现阶段用 RED/GREEN 与完整门禁证明。

## #9：建议 B，吸收 A 的简单运维

| 方案 | 机制与代价 | 判断 |
|---|---|---|
| A 整作品快照 | 每本书及全部版本存一个 JSON 行；实现快，但每次自动保存重写全书，SQL 难约束版本/章节，后续坏例关联成本高 | 不选 |
| B 作品＋版本产物 | Work 行、Artifact 每版本一行；内容/inputs 为 JSON；保留现有 Store 接缝，短事务内检查目标及上游基线并写入 | 推荐：最贴合已有语义，改动适中 |
| C 按产物拆表＋事件账本 | 各 kind 独立表，另存变更事件；可做复杂历史分析，但引入多套迁移与重放语义 | 超出本票 |

依据：`store/work-store.ts` 已有 append/save/finalize 和 preconditions；`in-memory-store.ts` 的 save 追加版本、finalize 同版原子通过；`start.ts` 当前每次启动都新建内存并 seed。#9 issue 明确同接口、迁移、版本与真实重启恢复。better-sqlite3 的事务封装遇异常回滚，适合此同步写入边界。[官方 API](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md#transactionfunction---function)

自主决定：持久化 Work/config、全部产物版本/status/inputs；维持公开 GET 只读 head，不新增历史 UI。数据库路径可配置；迁移有版本、失败不重置库；生产不无条件 seed，demo 显式且幂等。SQL 事务只包校验和写入，LLM 请求在外。保持当前生成锁＋提交条件；不做后台任务重启续跑。Skill 文件归属不变。默认不迁移旧内存演示数据，也不停止旧服务。

验收：内存/SQLite 共用 Store 测试；冲突及失败零新增；同版本通过；新版本保存；双连接竞争仅一个成功；创建两章并编辑历史章，真正终止/重启进程，内容/版本/状态/输入引用/衔接提示一致；第二次启动不重复示例。校验损坏数据与迁移失败明确报错。无新增人决点；若需切换用户旧服务且内有重要作品，再就保存路径单独确认。

## #7 Agent 配置

证据：[#7](https://github.com/12bitsD/agent4novel/issues/7) 保留三维偏好、每步 provider/model/SP/skills/tools 和上传 AC。`contracts/src/step.ts:11` 已声明 model/SP/skills/tools，却无三维偏好；`server/src/start.ts:48` 对所有步骤返回同一 work.config。`prose-step.ts:13` 只用构造参数 SP 或内置文件，不消费 config.systemPrompt。Wiki016 当前持有 provider HOW；ADR0002 明定 prompt/skill 存文件。`llm-call.ts:79` 已对最终系统文本取 hash、对模型结果运行 schema。

| 方案 | 收益 | 代价与适配 |
|---|---|---|
| A 每步完整独立配置 | 直观、无继承歧义，全部 AC 可做 | 六处重复设置偏好，改一本书容易漏步骤 |
| B 作品默认＋每步覆盖＋执行快照 | 三维一次配置，特殊步骤覆盖，能解释本次实际配置 | 需显式优先级、版本和解析后的只读预览；推荐 |
| C 跨作品可复用配置/Skill 库 | 多书复用、统一升级 | 引入共享版本升级和迁移选择；当前单用户 MVP 收益不足 |

推荐 B，借 A 的“每步实际配置可见”。默认三维偏好按服务端明确映射注入相应节点；高级区支持每步 model/SP/skill。每个生成操作开始冻结 config revision、选定 Skill 文件版本、解析后配置；同一 advance 内所有步骤使用该快照。运行中修改配置只作用于下一次新操作，本次按旧快照完成并可追溯；已有正文及通过状态不变。保存用 expectedConfigVersion，冲突不覆盖别人改动。

SP 是可编辑的写作指导；固定输出形状、ID 归属、预算及服务端校验不可覆盖。上传 Skill 只作提示文本，不执行脚本、不自动读相对文件/URL；tools 字段明确仅空/禁用声明，执行留 #28，不显示“已生效”假象。

遵守 ADR0002：正文文件按稳定 ID/hash 存入受管目录，数据库仅存选择/引用/revision；编辑 SP 也生成受管文件版本，避免数据库正文副本。新文件先原子写入再更新引用，失败不替换旧配置。备份包括 SQLite 与受管文件。Skill 仅 UTF-8 SKILL.md、校验必要元数据；统一大小/数量/装配预算，超限明确拒绝，文件名不参与服务端路径，前端纯文本预览。初始限额属于工程选项，实施时通过共享常量和边界测试锁定。

验收：fake 收到每步解析配置；真实一次调用能读到 model/config revision/Prompt hash；中途改配置不混用；重启仍解析原文件；非法模型、SP、Skill、超预算零调用；旧产物不变；上传内容不进日志。

Human：当前无需新增问题。只有要让 Skill 执行代码/tools、改 ADR 或引入跨作品联动升级时才升级为产品决定。

| 方案 | 收益 | 代价与适配 |
