# Ticket 完成审核清单 — 每票必须完整执行

每张 ticket 只有在第 1–6 节全部通过后，才能进入第 7 节的交付发布；第 7 节完成并回读验证后，ticket 才算完成。本文件是跨 ticket 完成流程的唯一权威来源；数字 Wiki 只保存该票的工程上下文与审核证据，不复制这套步骤。

## 使用约定

本清单的执行责任人是当前 ticket 的交付 Agent。开始规划或实现前完整读取一次，先执行 C1 与 C2 的前置项；实现候选形成后继续执行余下条目。

- “交付性远端写入”指推送交付分支、创建或更新交付 PR、merge、把 ticket/Project 改为完成态或关闭 issue。第 1–6 节通过前禁止这些动作。
- claim/assignee、`needs-info` 澄清、同步真实的进行中状态属于协作生命周期写入，可按 [issue tracker 规则](./issue-tracker.md) 在开工阶段执行，但必须记录；它们不能被包装成交付或关闭动作。
- 每项有稳定 ID，只允许记为 `PASS`、`FAIL` 或 `N/A（原因与风险）`。每个 `PASS` 条目都必须引用命令输出、代码位置、版本化计划、Human 决定、review 结论或远端回读；一份证据可以覆盖多个明确列出的 ID。`Ck = PASS` 表示该节所有未单列为 `N/A` 的 `Ck.x` 都是 `PASS`；所有 `N/A`、`FAIL` 与例外必须按条目 ID 单列。
- 空框表示每票都要重新执行，不在本文件内永久勾选。逐票证据按末尾“发布记录边界”写入本票 Wiki、GitHub issue 及可回读的远端状态。
- 任一 `FAIL` 都阻止交付。修复后重跑受影响条目；review 后只允许 C6.3/C6.5 定义的受控证据收口变化，它们必须由独立 reviewer 核对来源和精确 diff。任何行为、规范、AC、实现或其他文档事实变化都必须重新进入相应门禁与 review。
- 旧提交、修改前的测试和“应该没问题”不算证据。记录本次候选实际结果，但不把易漂移的测试数量写成规范。
- Human 只处理 Wiki skill 规定的保留裁决、产品取舍、新增权限或明确要求的人工作业；Agent 不能用等待 Human 代替可自主完成的检查。

## 1. 锁定票面与交付边界

先锁定 WHAT、验收标准和交付方式，完成条件是每个计划改动都能映射到 ticket，且工作区固定点已知。

- [ ] **C1.1** 按 [issue tracker 规则](./issue-tracker.md) 回读 GitHub issue 的标题、正文、评论、标签、状态、阻塞关系和 Project 字段；列出逐条 AC，并记录必要的 claim/澄清写入。
- [ ] **C1.2** 记录交付模式（目标分支直推，或工作分支 → PR → merge）、目标分支、PR source branch、分支保护、required checks/reviews 与当前授权。PR 模式必须在首个本地 commit 前创建或切换到 source branch 并核对 base；不得根据仓库习惯猜测本票是否需要 merge。
- [ ] **C1.3** 每张 ticket 都必须完成 grill/对齐并保存结论与 Human 决定；本地 Matt flow 可用时使用它，不可用时执行等价的范围、假设、风险与验收对齐。票面已有裁决可以作为输入，但不能替代本次核对。
- [ ] **C1.4** 按 `.claude/skills/agent4novel-wiki/SKILL.md` 建立或读取最小相关 Wiki，并核对 `CONTEXT.md`、相关 schema/ADR 与现行代码。
- [ ] **C1.5** 在实现前给出可执行计划（环境支持时使用 Plan mode），列出 TDD 切片、验证面与预期提交边界；计划变化时记录原因。
- [ ] **C1.6** 运行 `git status --short --branch` 与 `git branch --show-current`，记录固定点 SHA，确认当前分支符合 C1.2，并区分本票改动、已有用户改动与未跟踪文件；不得覆盖或夹带无关工作。
- [ ] **C1.7** 写出范围内、非目标、依赖与风险。新增范围必须回到 issue 或取得 Human 决定，不能在实现中静默扩票。
- [ ] **C1.8** 记录当前 ticket 完成时标签与 Project 字段的预期终态。仓库没有明确规则时保持原值并说明，不得在发布阶段现场猜测或顺手改关联票。

## 2. 核对 TDD 与实现

有可执行行为变化时必须保留可观察的失败与通过证据。纯文档、流程或无行为重构票可以把 RED/GREEN 记为 `N/A（无行为变化）`，但必须改用链接、schema、渲染或结构校验覆盖其 AC。

- [ ] **C2.1** 对新增或修复行为先得到 RED：测试因缺失目标行为而失败，而不是因夹具、环境或语法错误失败。
- [ ] **C2.2** 用最小实现得到 GREEN，再做不改变行为的整理；每个切片保持测试与 typecheck 双绿。每次仅本地提交前先检查 staged manifest、完整 patch、`git diff --cached --check`、凭据与范围归属，再按计划形成逻辑提交后进入下一片。
- [ ] **C2.3** 覆盖成功路径、边界、错误语义、版本/并发保护和跨包契约；无法自动化的 AC 写明人工验证步骤与结果。
- [ ] **C2.4** 检查实现是否沿用现有深模块与公共接缝，避免重复 helper、旁路状态机或引入票外抽象。
- [ ] **C2.5** 从最终候选反查每条 AC；没有对应证据的 AC 保持 `FAIL`。
- [ ] **C2.6** 对 C2.1/C2.2 记 `N/A` 的票，执行并记录与改动类型匹配的确定性验证；“只是文档”本身不是跳过验证的理由。

## 3. 跑本地质量门禁

本地门禁必须针对当前候选运行，输出不能被管道或截断掩盖。

- [ ] **C3.1** 先跑受影响包的定向测试，再从仓库脚本读取并执行完整测试、类型检查和构建命令；不适用的命令逐项说明。
- [ ] **C3.2** 运行格式/静态检查与 `git diff --check <fixed-point>`；检查生成物、锁文件和新增文件是否完整。未跟踪文件必须单独纳入检查，不能假定 `git diff` 已覆盖。
- [ ] **C3.3** 核对异常路径、日志与遥测没有泄露密钥、个人数据、完整 prompt 或供应商响应。
- [ ] **C3.4** 搜索本次候选中的凭据、危险命令、注入入口、无保护外部输入和意外联网；确认本地 secret 文件仍被忽略。
- [ ] **C3.5** 执行代码质量清理，并分别记录复用、可读性、边界归属和效率结论；优化不能改变 AC 语义。
- [ ] **C3.6** 记录命令、结果、日期和关键警告。环境原因造成的跳过只能记 `N/A（原因与风险）`，不能记 `PASS`。

## 4. 回写知识与用户文档

文档必须和最终行为一起进入 review；每个知识来源都要明确记为“已更新”或 `N/A（不受影响的原因）`。

- [ ] **C4.1** 更新本票数字 Wiki：`Agent Context`、技术方案、代码落点、测试与验证、边界、交接结论、路由 frontmatter 和必要的变化事件都与代码一致。
- [ ] **C4.2** 在本票 Wiki 的“测试与验证”预留 `### 完成审核证据`，格式以 [Wiki README](../wiki/README.md#完成审核证据) 为准；先填写已取得的证据，尚未发生的 review/裁决明确标为待完成。
- [ ] **C4.3** 数据形状或不变量变化时更新 `docs/schema.md`；领域词变化时更新 `CONTEXT.md`；否则记录不受影响的理由。
- [ ] **C4.4** 不可逆或跨票架构决定写 ADR；外部选型或实验依据写 research；Wiki 只链接其结论。没有这类变化时记录 `N/A`。
- [ ] **C4.5** 同步 `README.md` 与 `README.zh-CN.md` 的路线图状态；用户可见流程、安装、配置或限制变化时，同步两份对应说明和图示。
- [ ] **C4.6** 刷新 `docs/handoff.md` 的当前里程碑、关键约束、已知限制和下一票，删除或更新已漂移的快照。
- [ ] **C4.7** 运行方式、CLI、模型配置或排障流程变化时更新对应运行 skill；流程规则变化时更新 `docs/agents/` 或相关 Agent skill。其余情况记录不受影响。
- [ ] **C4.8** 校验本票 Wiki schema、固定标题、索引、issue backlink、本地链接，以及中英文 README 的事实一致性。
- [ ] **C4.9** 知识回写完成后、正式双轴 review 前执行三轮自校准并分别记录结论：① 代码 ↔ 行为/测试；② 代码 ↔ 最终 Wiki/领域词；③ 完整候选 ↔ issue AC/范围。

## 5. 冻结候选并做双轴 review

review 必须针对一个可标识的完整候选快照，Standards 与 Spec 两轴彼此隔离，且 reviewer 不得参与该候选的实现。

- [ ] **C5.1** 只暂存已获准的精确文件，回读 `git status` 与 staged name/status manifest，确认本票文件没有遗留在 unstaged/untracked 区，也没有夹带用户改动；记录固定点 SHA 与 `git write-tree` 得到的候选 tree。两轴通过时该 tree 记为 T0；任何实质修复都会生成新的 T0。
- [ ] **C5.2** 对 staged delta 运行 `git diff --cached --check`，并明确运行 `git diff --check <fixed-point> <candidate-tree>`。回读固定点到候选 tree 的完整 diff，确认新增文件、symlink、配置、锁文件、测试和文档均已纳入。
- [ ] **C5.3** 审计 `fixed-point..HEAD` 每笔本地 commit 的 name/status 与 patch，并审计 HEAD 到 candidate tree 的 staged patch，确保中间历史没有“加入后删除”的凭据、用户文件或票外内容。发现后禁止推送：先轮换可能暴露的凭据，再把仅本地历史整理为安全的交付历史并重新冻结。
- [ ] **C5.4** **Standards 轴**独立对照仓库指令、领域词、架构边界、安全规则、测试惯例与文档契约，报告文件位置和严重级别。
- [ ] **C5.5** **Spec 轴**独立逐条对照 GitHub issue 的 WHAT、AC、非目标与依赖，报告“满足 / 未满足 / 证据不足”。
- [ ] **C5.6** 两轴分别保留原始发现及其证据，再由交付 Agent 标记“接受并修复 / 有证据拒绝 / 剩余风险”；安全、逻辑、数据损坏或未满足 AC 的问题必须修复。
- [ ] **C5.7** review 后只要实质候选发生变化，就重新暂存、生成 candidate tree、重跑受影响门禁与相应 review 轴；不能沿用旧 tree 的结论。C6.3/C6.5 的受控证据收口不属于实质变化，但必须按各自条目独立核验。

## 6. 修复、回归并取得发布前裁决

完成条件是所有阻塞发现关闭，实质候选获得独立裁决，并且该裁决通过一个有终点、不会要求 tree 自我记录自身哈希的证据收口写入最终候选。

- [ ] **C6.1** 为 review 暴露的行为缺陷补 RED 测试，再修复到 GREEN；文档缺陷直接修正并重跑对应结构/链接校验。
- [ ] **C6.2** 重新暂存精确文件并重跑受影响测试与第 3 节门禁；修复改变行为、契约、文档事实或 AC 映射时，重跑对应 review 轴。
- [ ] **C6.3** 在本票 Wiki 的预留字段写入 T0，并忠实转录已取得的 C1–C5、C6.1/C6.2、AC/TDD、本地门禁、双轴结论、修复、知识维护、全部 `N/A`/例外与剩余风险；T1 和“发布前裁决”保持 `pending`。这是仅能修改预先声明证据字段的受控变化。
- [ ] **C6.4** 重新暂存并用 `git write-tree` 生成 pre-attestation tree（T1）。由未参与实现的 reviewer 精确比较 T0 → T1，确认只改了 C6.3 预留字段且忠实于原始输出；同时检查 T1 的完整 diff、逐笔本地 commit、工作区余项和证据映射，明确给出 `PASS` 或 `FAIL`。证据转录错误回到 C6.3，其他变化回到 C5.7。
- [ ] **C6.5** reviewer 为 `PASS` 后，只在预留字段一次性写入清单 blob、固定点 SHA、T1、C1–C5 分节判定、C6.1–C6.4 逐项证据与 reviewer attestation，再重新暂存该 Wiki，生成最终交付 tree（T2）。Wiki 记录 T0/T1，不尝试让 tree 记录自己的哈希，也不提前宣称整节 C6 已通过。
- [ ] **C6.6** 同一 reviewer 或第二位独立 reviewer 精确对比 T1 → T2，确认唯一变化是 C6.5 获准字段且内容忠实于原始证据；给出终止性的 `PASS` 或 `FAIL`。这个比较结果不再写回同一候选；C6.5 字段错误修正后重做本条，来源证据错误回到 C6.3–C6.4，任何其他变化回到 C5.7。
- [ ] **C6.7** 列出准备提交的精确文件，按逻辑边界设计提交，并再次确认没有 secret、临时文件或其他人的改动。

## 7. 提交、推送、合并与远端确认

远端只能接收已经冻结的候选。完成条件是交付分支、CI、merge（如适用）和当前 ticket 状态都已回读确认。

- [ ] **C7.1** 确认或补齐逻辑提交并验证 `HEAD^{tree}` 等于 T2；随后再次审计 `fixed-point..HEAD` 每笔 commit 的 name/status、完整 patch、凭据与范围归属，覆盖 C6 后新形成或整理的所有提交。commit hook 若改写文件，返回第 3 节并使旧 review tree 失效。
- [ ] **C7.2** 先回读远端目标分支并确认实际交付 diff 仍等于已审核候选；base 漂移、rebase、merge conflict 或其他历史整理只要改变交付 diff/tree，就返回 C5。确认后按 C1.2 执行：直推模式推送目标分支并核对远端 HEAD；PR 模式推送 source branch、创建或更新 PR、核对 PR diff、等待 required checks/reviews、在获得所需授权后 merge，并确认目标分支包含已审核的结果。
- [ ] **C7.3** 回读仓库实际 CI 与必需检查。有 CI 时记录对应 commit/PR 的结果；没有时记 `N/A（仓库未配置 CI）`，不得用本地测试冒充 CI。
- [ ] **C7.4** 只按 C1.8 记录的终态核对并更新当前 ticket 真实存在的依赖边、[规范标签](./triage-labels.md)和 Project 字段。依赖边默认保留；只有票面证据或 Human 决定证明关系错误时才改，关联 ticket 不自动联动。未加入 Project 时记 `N/A`。
- [ ] **C7.5** 只有 AC 全部满足、审核结果已在目标分支可见且必需检查通过后，才准备最终完成摘要。摘要链接已提交的本票 Wiki，只摘要 AC 状态，并记录 commits、PR/merge、CI、C6.5–C6.7 逐项证据与最终 `C6 = PASS`、当前 ticket 元数据、计划采用的关闭方式/条件和剩余风险；不复制 Wiki 中的本地门禁和 review 全文，也不预写尚未发生的关闭结果。
- [ ] **C7.6** 按 [issue tracker 规则](./issue-tracker.md) 发布 C7.5 摘要并关闭当前 issue：普通 issue 使用 `gh issue close --comment`；若适用流程明确要求 comment → close，则先发布并回读评论再关闭。绝不先关闭再补完成评论。命令完成后回读 issue 状态、依赖、标签/Project 与评论；live issue state 是关闭结果的权威证据。
- [ ] **C7.7** 再次回读远端目标分支，确认提交可达，且本地工作区符合预期。

## 发布记录边界

每票的持久记录分 Wiki 与 GitHub 完成评论两处保存；终止性结果由可回读的 issue、PR、CI 和分支状态直接作证。这样避免为记录“已经推送”再制造一个需要重新推送的文档提交。

- **数字 Wiki**保存发布前证据：清单文件的 blob 标识、固定点 SHA、T0、pre-attestation tree（T1）、C1–C5 分节判定、C6.1–C6.4 逐项证据、所有相关 `N/A`/例外、AC/TDD、本地门禁、双轴 review、修复、知识维护、剩余风险和发布前 attestation。它不记录最终 tree（T2）或整节 C6 判定，避免自引用与提前断言。
- **GitHub issue 完成评论**链接该 Wiki，保存 commits、PR/merge、CI 实际状态、C6.5–C6.7 逐项证据与最终 `C6 = PASS`、当前 ticket 元数据、关闭方式/条件和剩余风险。关闭结果以评论发布后的 live issue state 为准；C7 的终止性回读不再写回同一评论。

任一证据缺失时，ticket 仍处于未完成状态；下一位 Agent 从缺失项继续。只有候选 tree 未变化时，才可复用已有证据。
